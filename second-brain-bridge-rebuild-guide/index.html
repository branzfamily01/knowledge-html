STEP 1

GitHub Pagesで動く最小Bridgeを作る

目的

公開起点とファイル構造を確定する。

主要ファイル

Codexに渡す指示

STEP 2

端末保存を先に「消えない設計」にする

目的

通信や他UIが壊れても入力データを失わない。

主要ファイル

storage-v2.js / ui-storage-safety.js

入力→write queue→IndexedDB↘localStorage予備
  • IndexedDB初期化前のsaveを保持する。
  • IndexedDB失敗時はlocalStorageへfallbackする。
  • QuotaExceededや保存失敗を無言で成功扱いしない。
  • pagehide中の同期予備保存も考慮する。
  • 復旧時は「消失」より「一時的な復活」を優先し、後のtombstoneで解決する。
Codexに渡す指示
Second Brain Bridgeのローカル保存P0を実装する。
IndexedDBを主保存、localStorageをfallback/予備保存とする。
初期化前save、書込失敗、QuotaExceeded、restoreとの競合、pagehideをテストする。
保存成功前に旧データを消さない。
保存UI以外のJSが壊れても保存層がロードされるよう静的依存にする。

テスト：保存→reload、オフライン保存→reload、IndexedDB故障注入、restore/save同時実行。

STEP 3

Supabaseに「現在状態」と「履歴」を分けて作る

目的

複数端末で同期しつつ、過去の変更も失わない。

主要ファイル

sync.js、Supabase tables / RLS / migration。

層役割原則
bridge_items現在状態更新可
bridge_item_history変更履歴追記専用
bridge_contextContext現在状態
注意

RLSはユーザー本人のrowだけを読み書きできるようにする。publishable keyを使うこと自体ではなく、RLSが境界になります。

Codexに渡す指示
Supabase同期を追加する。
current stateとappend-only historyを分ける。
RLSはauth.uid() = user_idを基本に設計し、他ユーザーrowへアクセスできないことを確認する。
ローカルとクラウドの競合、同期中に発生したローカル編集を失わないテストを追加する。
STEP 4

通常削除をtombstone化する

端末Aで削除したものが、端末Bや古いキャッシュから再登場する問題を防ぎます。

やってはいけない

単純にrowを消す → 他端末が「存在しない=新規」と判断して復活。

採用方式

deleted_atを持つtombstoneを同期 → 全端末が削除済みIDを知る。

  • tombstone rowのライブpayloadはnull。
  • 削除と後着編集が競合したら削除優先。
  • Obsidianには削除を伝播しない。
  • 履歴の過去本文はこの操作では消さない。
Codexに渡す指示
通常削除をphysical DELETEではなくtombstoneへ変更する。
deleted_atを全端末へ同期し、削除済みIDを再upsertしない。
tombstone payloadはnullにする。
削除と遅れて到着した編集が競合したら削除優先。
履歴とObsidian archiveは削除しない。
DB migrationを先に適用してからclientを配布する手順も文書化する。
STEP 5

全データリセットにreset_epochを入れる

全リセット後、古い端末やPC Agentがリセット前データをクラウドへ戻す事故を防ぎます。

reset開始marker→cloud epoch +1→current rows物理削除→local消去→marker解除
  • bridge_reset_stateにユーザーごとのepoch。
  • bridge_items.reset_epochを持たせる。
  • 古いepochのwriteはDB triggerで拒否。
  • 全リセット中断時は次回起動で再開。
  • 初回同期端末の未同期ローカルデータはepoch差だけで自動消去しない。
Codexに渡す指示
全データリセット専用RPCとreset_epochを実装する。
通常削除のtombstoneとは分離する。
RPCはepochを先に進め、その後current stateを本人分だけ物理削除する。
古いepochのupsertをDBで拒否する。
リセット途中markerを端末に残し、中断後に再開できるようにする。
PC Agentもepoch上昇を検出したら自動停止し、明示resumeまで旧データを再投入しない。

STEP 9

Obsidian Agentを「一方向・追記専用」で作る

bridge_items current rows→intake gate→schema normalizer→append-only writer→00_Capture/YYYY/MM
  • historyをCapture event streamとして使わない。
  • tombstoneは新規noteを作らない。
  • 既存Markdownを編集・移動・削除しない。
  • AgentからBridgeへ処理結果を書き戻さない。
  • identityはaccount + reset_epoch + bridge_items.idからSHA-256。
identity = sha256(accountId + NUL + reset_epoch + NUL + bridge_items.id)
capture-<64hex>.md
Codexに渡す指示
Bridge current rowsをObsidianへ一方向にarchiveするAgentを作る。
既存noteは絶対に上書き・削除・移動しない。
filesystem identityは authenticated account + reset_epoch + bridge_items.id のSHA-256。
tombstoneは新規noteを作らない。
同一identityは起動時scanとexclusive create(wx)の両方で重複防止する。
AgentからBridgeへwritebackしない。

STEP 13

テスト → PR → Solレビュー → 修正 → merge

Second Brain Bridgeでは、実装完了を「コードを書いた」ではなく「壊し方をテストし、レビューでblockerが消えた」と定義します。

Codex実装→targeted tests→P0 full tests→PR→Sol review→修正→re-review→merge
Solに渡すレビュー指示
このPRをSecond Brain Bridgeの現行方針を正本としてレビューしてください。
仕様変更の影響は Maintain / Modify / Retire / Hold に分類してください。
データ消失、削除復活、reset epoch、account境界、append-only、外部入力、network、既存機能回帰を重点監査してください。
blockerは再現条件・影響・最小修正・追加すべき回帰テストまで示してください。

重要：自動テストgreenだけで完了にしない。GitHub Pages、iPhone/Safari、Windows launcher、実X sessionなど、CIで再現できない部分は公開後smokeを別gateにする。

理解チェック

Q1. なぜUIより保存層を先に作る？

Bridgeの最重要価値はデータを失わないことだから。保存層をUI依存にすると、無関係なUI障害で保存まで壊れます。

Q2. 通常削除と全リセットの違いは？

通常削除はtombstoneで削除済みIDを共有。全リセットはreset_epochを進めて現在状態を物理削除し、旧epochからの復活をDBで拒否します。

Q3. Obsidian Agentが既存noteを編集しない理由は？

Obsidianを人間可読の長期archiveとして守るため。Bridge側の削除・変更・失敗を過去のarchiveへ破壊的に伝播させません。

Q4. schema 0の既存itemを全部schema 1へ書き換えない理由は？

不要な履歴・同期競合を増やさず、過去itemを現在writer生成と偽装しないため。Agent入口で正規化します。

Q5. CodexとSolの役割は？

Solは設計・仕様・原因分析・レビュー。Codexはファイル編集、CLI、テスト、Git、PRなど実行作業。重要な仕様変更は採択前に実装確定しません。

この手順書の位置づけ

これは「Second Brain Bridgeの操作マニュアル」でも「一般アプリ開発入門」でもありません。2026-08-31時点のSecond Brain Bridge main実装、P0保存契約、Capture Schema v1、Windows PC Agent、Obsidian Agent、Knowledge HTML連携、AI協働ルールをもとに、同じBridgeを再構築する順序へ再編集した専用runbookです。
