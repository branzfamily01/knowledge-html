LEVEL 2｜3〜5分

最初から最後までの実際の使い方

01

素材を渡す

ChatGPTとの会話、PDF、画像、URL、メモ、コード、教科書、授業資料などを素材にできます。会話の場合は全文をそのまま並べず、疑問・誤解・理解につながった説明・結論を抽出して再構成します。

02

一言で依頼する

この話を初心者向けHTMLにして保存して

これが基本コマンドです。特別な指定があるときだけ「Publicで」「図を多めに」「このコードは省略しない」などを足します。

03

ChatGPTが内容を再設計する

入力をそのままHTML化するのではなく、情報抽出、重複整理、構造化、因果整理、重要度判定、図解方法選択、初心者向け再設計の順に処理します。

抽出→整理→構造化→図解→HTML
04

「Knowledge」か「Web App」かを判定する

判定主目的保存先
Knowledge読む・理解する・調べるknowledge-html/<slug>/
Web App入力・保存・生成・同期・ゲーム進行・作業実行原則 1アプリ＝1 GitHubリポジトリ
05

Knowledge HTMLをGitHubへ保存する

Knowledgeの場合は、英小文字とハイフンでslugを決め、4ファイルを作ります。

<slug>/
├─ index.html
├─ style.css
├─ script.js
└─ metadata.json
06

metadata.json を作る

HTMLのタイトル、分類、タグ、要約、公開URL、情報源などを機械が読める形で記録します。これは「本の背表紙＋図書カード」のような役割です。

やさしい意味このHTMLが何なのかを説明する名札正式名称metadata正確には検索・台帳更新・再利用に使う構造化データ
07

registry.json に登録する

各Knowledgeのmetadataから、中央台帳であるregistryへ1件追加します。My HubやSecond Brain Bridgeは、この台帳を読むことでKnowledgeを見つけられます。

metadata.json→registry.json→My Hub
08

GitHub Pages で公開する

mainブランチの更新がGitHub Pagesへ反映され、ブラウザで読めるURLになります。KnowledgeのURLは原則、knowledge-htmlの下にslugが続く形です。

https://branzfamily01.github.io/knowledge-html/<slug>/
09

最後に My Hub へ入る

My HubはGitHub上の実体を移動させる場所ではありません。KnowledgeのregistryとWeb Appsの台帳を読み、「人間が見て探すための玄関」にします。新しいKnowledgeがregistryへ入れば、My HubのKnowledge一覧にも現れます。

保存先を決める3つの分岐

分岐1

読む？ 使う？

読む・理解するならKnowledge。操作して何かを実行するならWeb Appです。

分岐2

Publicで大丈夫？

一般知識はPublic。個人・家族・学校などの情報が入るならPrivateや匿名化を検討します。URLを知っているだけで守られる、という考え方はしません。

分岐3

昔のChatGPT作品？

GitHub導入前のアプリはMy HubのRescue台帳へ入れ、原本発見、重複確認、Privacy確認、GitHub救出の順で処理します。

LEVEL 3｜しっかり理解

裏側では何が起きている？

GitHub

ファイルの正本、変更履歴、公開元。倉庫兼タイムマシンです。

registry.json

Knowledgeの中央台帳。何がどこにあるかを機械が読めます。

GitHub Pages

GitHubにある静的HTMLを、ブラウザで開けるWebページとして配信します。

My Hub

KnowledgeとWeb Appsを、人間がカード・検索・カテゴリで探す入口です。

Second Brain Bridge

registryを読み取り専用カタログとして検索する層です。Knowledge本体を通常データへ混ぜません。

ChatGPT

素材理解、再設計、保存、台帳更新、発掘、検索を会話でつなぐオーケストレーターです。

なぜHTMLは「結論 → 全体像 → 詳細」なの？

初心者は、細部から読むと「今どこを説明しているのか」を見失いやすいからです。まず結論で目的地を示し、全体像で地図を見せ、その後に詳細へ降ります。難しい情報を削るのではなく、認知負荷を下げるために順番を変えます。

情報を削らず、視界だけ軽くする方法

必須情報は常時表示し、補足・発展・長いコードはdetailsなどで折りたたみます。「情報は全部残すが、視界には必要なものだけ出す」が基本です。

My Hubに直接ファイルを置かないのはなぜ？

My Hubは入口だからです。Knowledgeやアプリ本体をMy Hubへコピーすると、同じものが複数箇所に存在し、どれが正本か分からなくなります。正本はGitHubの各保存先に置き、My Hubは台帳を読んでリンクするだけにします。

注意

よくある間違い

× 入力文をそのまま長いHTMLにする→ 構造化・図解・階層化してからHTMLにする。
× 難しい部分を削って「簡単」にする→ 難しい部分ほど分解して残す。
× アプリも全部knowledge-htmlへ入れる→ 本格Webアプリは独立リポジトリ。
× URLが推測できるから登録する→ 実際の公開URLを確認してから台帳へ登録する。
× 個人情報入りHTMLをPublicへ置く→ Private・匿名化・Accessなどを検討する。
× My Hubを正本にする→ My Hubは入口。正本はGitHub側。

理解チェック

5問だけ確認

Q1. 一番簡単な依頼文は？

「この話を初心者向けHTMLにして保存して」です。

Q2. KnowledgeとWeb Appの一番大きな違いは？

主目的です。読む・理解するものがKnowledge、操作して作業を実行するものがWeb Appです。

Q3. registry.json は何のため？

Knowledgeの中央台帳です。My Hubや検索側が、タイトル・要約・URLなどを見つけるために使います。

Q4. My Hubは保存場所？

いいえ。My Hubは入口です。正本はGitHubの各リポジトリに置きます。

Q5. GitHub導入前の昔のアプリは？

Rescue対象として発掘し、原本・後継重複・個人情報を確認してからGitHubへ救出します。

つまり

素材を渡す → 一言で頼む → My Hubまで任せる。

このプロジェクトの目的は、HTMLを作ること自体ではありません。理解した内容を、消えず、探せて、また読める知識資産にすることです。
