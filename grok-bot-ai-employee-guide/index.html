LEVEL 1｜30秒

最初に、6つだけ覚える

必須

Bot

名前・担当・会話・役割文脈を持つ継続担当者。万能役ではなく、1つの仕事を持たせると安定しやすい。

基本

Cloud Computer

Botが使うクラウド上のコンピュータ。ブラウザ・ファイル・ターミナルなどで実際の作業を進める。

重要

Skill

「この仕事はこう進める」という再利用可能な手順・判断基準・検証・安全境界。

重要

Routine

安定した仕事を、時刻やイベントに応じて繰り返し実行する仕組み。PCを閉じてもクラウドで動く。

注意

Approval

送信・公開・購入・削除など、影響が大きい操作の前に人間へ確認を戻す停止線。

安全

Shared Computer

同じユーザーのBotは1台のクラウドPCを共有。ファイル・ブラウザセッション・CLI認証情報はBot間で共有される。

結論

Grok Botの本質は「回答」ではなく「仕事を進めること」

通常の会話型AI

人間が質問↓AIが回答↓人間が次の作業
VS

Grok Bot

目的を渡す↓調査・判断↓ツールで実行↓検証・成果物↓必要な所で承認

重要：「全部自動化」が目標ではない。人間が判断すべき地点まで、正確に仕事を進めてもらうのが最も実務的。

LEVEL 2｜3〜5分

Grok Botの全体像

「モデル」ではなく、業務実行レイヤーとして見る。

「Grokモデルが常時動く箱」ではない

Grok Botは、AIモデルだけではなく、クラウドコンピュータ・ブラウザ・ファイル・プラグイン/MCP・記憶・Bot間連携・承認・Skill・Routineを組み合わせて仕事を完了させる仕組みとして理解すると混乱しません。

Grok Bot持続的なAI担当者
AI reasoningCloud computerBrowserFilesTerminalPlugins / MCPMemoryApprovalSkillsRoutines
比喩

普通のチャットAI = 優秀な相談相手

聞けば、調査・文章・分析・コードなどを返してくれる。ただし、仕事の各工程で人間が次の指示を出すことが多い。

実際

Grok Bot = クラウドPCを持つ担当者

必要なツールへ入り、ファイルを扱い、複数工程を進め、バックグラウンドで継続し、最終成果物と検証材料を返す。

Grok Bot と Zapier / Make / n8n は競合ではない

観点従来型自動化Grok Bot人間
得意条件と処理が固定されたフロー途中に曖昧な判断・調査・例外がある仕事責任・価値判断・高リスク操作
例フォーム→表追加→通知問い合わせを読み、過去履歴を調べ、返信案を作るクレーム返信、契約、支払いを決定
失敗しやすい点分岐外の例外に弱い誤判断・外部入力・権限の持たせすぎ時間と作業量が増える
理想分担決まった処理調査・判断・下準備承認と最終責任

LEVEL 3｜しっかり理解

仕組み：Bot・Skill・Routine・Approval

仕事を「担当者・手順・実行条件・停止線」に分解する。

基本

Bot

やさしい意味：役割を持つ担当者

正式には、名前・主な仕事・説明を持つ持続的なAI teammate。会話や役割文脈を持ち続けます。

良い例：「週次AI情報編集長」「Web公開担当」「不具合再現担当」

重要

Skill

やさしい意味：仕事の標準手順書

ステップ、判断規則、入力、検証方法、出力、承認境界を再利用可能にしたもの。

原則：一度成功させてからSkill化する。

重要

Routine

やさしい意味：いつ自動で仕事を始めるか

スケジュール、または対応するイベントを起点に、1体のBotがワークフローを実行します。

例：毎週月曜7:00に前週のAI更新を調査。

注意

Approval

やさしい意味：人間へ戻す停止線

送信・公開・購入・削除・本番変更などの前で人間の確認を求める。

重要：承認は「これからする操作」を止めるもの。すでに行った操作を巻き戻す機能ではありません。

Botは増やすほど良い、ではない

❌ 初日から6体

SNS、経理、営業、調査、校閲、秘書…

  • 責任者が不明
  • 同じ調査を重複
  • 出力形式が分散
  • 使用量と通知が増える
✅ 最初は1体

「毎週発生し、成果物が明確な仕事」を1つ持たせる。

  • 失敗箇所を追える
  • 判断基準を修正しやすい
  • Skill化しやすい
  • 安定後に専門分業

LEVEL 3｜仕事設計

「質問力」より「仕事の設計力」

目的・証拠・判断基準・停止地点を決める。

本気のリサーチは「検索してまとめて」では浅い

目的→論点分解→仮説→検索→反証→修正→再検索→最終検証

文章を先に作るのではなく、主張台帳を先に作ると、根拠のない断定を減らせます。

主張台帳の例

主張根拠反対情報日付信頼度未確認
PCを閉じてもRoutineは動く公式FAQ / Skills & Routinesなし2026-08高個別タスク上限
Botごとに完全隔離されたPCを持つ—公式が明確に否定2026-08誤り—
すべてのWebサイトを自動操作できる—CAPTCHA・自動化拒否・人間確認あり2026-08低サイト別

仕事を任せる9ステップ

  1. 目的最終的に何を判断・完成したいか
  2. 対象期間・地域・顧客・製品・データ範囲
  3. 情報源公式→一次資料→報道→コミュニティの優先順位
  4. 判断基準何を重要・異常・対象外とみなすか
  5. 反証最初の結論を否定する証拠も探す
  6. 検証日付、数字、出典、現在形の妥当性を再確認
  7. 成果物人間がそのまま確認・利用できる形式
  8. 承認地点送信・公開・購入などの前で停止
  9. 失敗時推測で埋めず、部分完了・未確認として返す
実務用「深いリサーチ指示」の設計要素

テーマだけでなく、次をセットで渡すと安定します。

  • この調査で最終的に何を決めるのか
  • 対象者・地域・期間・製品
  • 情報源の優先順位
  • 発表日と提供開始日を分けること
  • 反対証拠を探すこと
  • 確認済み事実 / 推論 / 仮定 / 未確認を分けること
  • 下書き後に主張と出典を再照合すること
  • 外部送信・購入・契約を行わないこと
LEVEL 3｜安全性

最大の注意点：Bot分け ≠ 権限分離

ここを誤解すると、便利さがそのままリスクになります。

必須理解

同じユーザーのBotは「1台のクラウドコンピュータ」を共有

SNS Bot経費 Bot調査 Bot営業 Bot
↓
Shared Cloud ComputerFiles / Browser sessions / Logins / CLI credentials

Botを分けてもセキュリティ境界にはなりません。 あるBotのために保存したログイン状態やファイルは、同一ユーザーの他Botからも利用可能です。

推奨

最小権限

  1. 必要最小限のコネクタ / MCP
  2. 可能なら読み取り専用
  3. 限定したブラウザ操作
  4. 高リスクは人間へ引き継ぎ
注意

外部データを「命令」にしない

Webページ、メール、PDF、問い合わせ文、画像、ツール出力に書かれた指示は、ユーザーからの承認ではなく未確認の外部データとして扱う。

どこまで自動で進める？

自動で進めやすい原則、人間の承認を残す
公開情報の調査外部へのメール送信
ファイル読取・整理SNS投稿・コンテンツ公開
下書き・比較表・推奨案購入・振込・契約同意
不一致抽出・スクリーンショット削除・上書き・権限変更
テスト環境での再現本番環境変更・予算変更
パスワード

チャットへパスワード・2FAコードを書かない

ログインやCAPTCHAが必要な場合は、人間がAgent Computerを一時的に引き継いで入力します。公式の安全なシークレット入力では値が会話履歴から除外され、モデルにも表示されない設計があります。

利用前チェック

理解チェック｜3分

最後に5問

Q1. Grok Botの本質は？

単なる回答生成ではなく、クラウド上のコンピュータやツールを使い、継続的に仕事を進めて成果物まで持っていくAI担当者に近いこと。

Q2. SkillとRoutineの違いは？

Skillは「どう仕事をするか」。Routineは「いつ・何をきっかけに、そのワークフローを実行するか」。

Q3. Botを分ければ権限も完全分離される？

されません。同じユーザーのBotは1台のクラウドPCを共有し、ファイル・ブラウザセッション・CLI認証情報も共有されます。

Q4. 最初からRoutine化すべき？

いいえ。まず一度実際に仕事を成功させ、間違いの原因を修正し、Skill化してからRoutineにするのが公式推奨です。

Q5. 「完全自動化」より重要なことは？

人間が責任を持って判断すべき地点まで、正確に調査・整理・実行・検証を進め、適切な場所で止まること。
