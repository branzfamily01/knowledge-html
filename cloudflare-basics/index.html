LEVEL 2｜注意

初心者が踏みやすい3つの落とし穴

注意 1

雲を全部オレンジにしない

Proxyできるのは主にWeb通信に使うA / AAAA / CNAME。 MXやTXTはProxy対象ではなくDNS-onlyです。メールやドメイン認証に使うホストも、用途を確認して設定します。

Web用 A/AAAA/CNAME → 🟠 ProxiedMX/TXT → DNS only
注意 2

Flexibleを安易に選ばない

利用者🔒Cloudflare🔓Origin

FlexibleはCloudflare→OriginがHTTPです。ログインや個人データを扱うなら特に避け、Origin側が対応できるならFull (strict)を基本にします。

注意 3

人ごとに違う画面を雑にキャッシュしない

Cloudflare CDNはHTML/JSONを標準ではキャッシュしません。Cache Rulesで動的ページをキャッシュするときは、ログイン状態・Cookie・個人情報を必ず考慮します。

画像/CSS/JS → 標準でキャッシュ対象になりやすいHTML/JSON → 標準では対象外

よくある言い方より正確な理解
MXは灰色の雲にするMX自体はProxy不可で常にDNS-only。さらにメール配送に使うA/CNAME等も用途確認が必要。
Flexibleは絶対ダメ特殊事情では使えるが、OriginがTLS対応できるならFull / Full (strict)を優先。機密情報を扱うならFlexibleは避ける。
キャッシュで負荷が8〜9割減る削減率はサイト構成とキャッシュヒット率次第。固定の数字として一般化できない。
Cloudflareはサイトの手前の門番それに加えてWorkersで「Cloudflare自身が実行場所」になる構成もある。
LEVEL 3｜しっかり理解

ここから先は実務の仕組み

1｜オレンジの雲は何を変える？

DNSレコードが Proxied になると、WebのHTTP/HTTPS通信がCloudflareネットワークを通ります。CloudflareはそこでTLS終端、キャッシュ、WAF、DDoS対策などを適用できます。

DNS-only

利用者 → Origin

CloudflareはDNS回答をするが、Web通信自体は通らない。

Proxied

利用者 → Cloudflare → Origin

CloudflareがWeb通信の途中に入る。
2｜SSL/TLSは「2本の通信」で考える

CloudflareをProxyとして使うと、通信は「利用者↔Cloudflare」と「Cloudflare↔Origin」の2区間になります。

Visitor🔒 HTTPSCloudflare🔒 HTTPS + 証明書検証Origin

Full (strict)では両区間を暗号化し、CloudflareがOrigin証明書の有効性とホスト名一致も確認します。Originに有効な証明書が必要です。

3｜Workers Static Assetsは何をしている？

Workers Static Assetsでは、HTML・CSS・JavaScript・画像などをWorkerプロジェクトと一緒にDeployできます。静的ファイルはCloudflareネットワークから配信され、必要ならWorkerコードと組み合わせてAPIや認証処理も実装できます。

{
  "name": "my-app",
  "compatibility_date": "2026-09-10",
  "assets": {
    "directory": "./dist"
  }
}

これは仕組みを理解する最小例です。実案件ではビルド出力先やWorkerコード有無に合わせて設定します。

4｜Cloudflare Accessはどこで本人確認する？
ブラウザ→Access Policy許可 →アプリ

Accessはアプリより手前でポリシーを評価します。Allow / Block / Bypass / Service Authなどのアクションと、メール・国・端末状態などの条件を組み合わせます。

重要：「URLが秘密だから安全」ではありません。限定公開したいなら、URLの秘密性ではなく認証・認可で守ります。

技術的注意 WorkerレベルのAccessはRoute・Custom Domain・workers.dev・Preview URLをまとめて保護できます。ただし2026年9月時点ではWorkerレベルAccessはWebSocketをサポートしないため、WebSocketを使うアプリはhostnameベースのAccessを使います。

5｜Cacheは「何でも保存」ではない

標準では画像、CSS、JavaScriptなど特定拡張子の静的ファイルがキャッシュされやすく、HTMLやJSONは標準ではキャッシュされません。Cache-Control、Cookie、HTTPメソッド、Cache Rulesなどでも動作が変わります。

危険：ログイン後のHTMLを「Cache Everything」のような広いルールで保存すると、利用者ごとの情報が混ざる設計になり得ます。ルールを作る前に「誰が見ても同じ内容か」を確認します。
6｜Public / Private / Pendingの使い分け
Public｜公開

一般知識。GitHub Pages等で公開可能。

Private｜非公開

個人・学校・業務内部情報。一般公開しない。

Pending｜未判断

迷ったら公開しない。Private相当で扱う。

Cloudflareは「Publicしか置けないサービス」ではありません。Accessなどを組み合わせれば、公開URLを持ちながら認証された利用者だけに見せる構成も作れます。

7｜Pages / Workers Static Assets / workers.dev の違い
項目PagesWorkers Static Assets
基本モデルPages projectWorker projectの一部として静的ファイルを持つ
静的配信得意得意。Workerコードとも一体化できる
サーバー側処理Functionsで対応Worker scriptを同じプロジェクトで実行
新規構成継続利用可能新規の静的/フルスタック構成で中心になりやすい

Pages の既定URLは *.pages.dev、Workers の既定URLは *.workers.dev です。workers.dev はWorkerをすぐ試す用途に便利ですが、Cloudflareは重要な本番用途ではCustom DomainやRouteを推奨しています。Preview URLもAccessで保護できます。

8｜Private GitHubから自動Deployできる？

できます。 Workers BuildsのGit連携はGitHub / GitLabをサポートし、pushごとに自動Deployできます。Private repositoryを使う場合は、Cloudflare GitHub Appに必要なリポジトリだけを許可する設計が安全です。

Private GitHub→Workers Builds→Static Assets / Worker

GitHubを使わず、Wrangler CLIから直接Deployすることも可能です。GitHubは必須ではなく、履歴・差分・復旧のための「正本」として使うのが分かりやすい運用です。

9｜OTPとZero Trust Freeはどう使う？

Cloudflare Accessでは、外部IdPを使わずメールでOne-time PIN（OTP）を送る方式も設定できます。許可ポリシーに入っているメールアドレスだけがPINを受け取れます。

2026年9月時点のCloudflare公式料金では、Zero Trust Freeは50ユーザー上限です。少人数の限定公開には人数面で収まりやすい一方、ログ保持・サポート・他機能の上限は別に確認が必要です。

10｜Netlifyなど他サービスとの違い

CloudflareだけがWeb公開の正解ではありません。NetlifyなどもGit連携、静的サイト、Functions、限定公開の仕組みを持ちます。Cloudflareを選ぶ強みは、DNS・Reverse Proxy・CDN・Access・Workersを同じネットワーク基盤で組み合わせやすい点です。

サービス選択は「有名だから」ではなく、公開範囲・認証・サーバー処理・運用コスト・管理場所を見て決めます。

SECURITY｜重要

限定公開でも「何でも置いてよい」ではない

低〜中機密

限定共有の知識HTML

一般には公開したくないが、許可した少人数で共有する内容。Private GitHub + Workers + Accessは有力な構成です。

高機密

個人情報・内部情報

Accessだけで十分とは限りません。MFA、短いSession、端末管理、監査、保存場所、法令や組織ポリシーも検討します。

秘密情報

パスワード・秘密鍵・API Secret

HTMLやGitに保存しない。 Secret ManagerやPassword Managerへ分離します。

Private repository ≠ Private website。 リポジトリがPrivateでも、別の公開処理で生成されたWebサイトが自動的に非公開になるとは限りません。閲覧側の認証・認可を別に設計します。

理解チェック

5問だけ。答えはタップで表示

Q1. Cloudflareは「別サーバーを守る」だけのサービス？
答え：いいえ。 ProxyとしてOriginを守る構成に加えて、WorkersでCloudflare自身がアプリの実行場所になる構成もあります。
Q2. MXレコードはオレンジの雲にできる？
答え：できません。 MXやTXTはProxy対象ではなくDNS-onlyです。
Q3. Full (strict)では何を確認する？
答え：Cloudflare→Originも暗号化し、Origin証明書の有効性とホスト名一致を検証します。
Q4. GitHub PrivateならWebサイトも自動でPrivate？
答え：いいえ。 GitHubのリポジトリ権限と、公開されたWebアプリの閲覧権限は別です。
Q5. HTMLはCloudflare CDNで必ず標準キャッシュされる？
答え：いいえ。 通常のCloudflare CDNではHTML/JSONは標準キャッシュ対象ではありません。必要ならCache Rules等で設計します。
