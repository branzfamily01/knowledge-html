よくある誤解を先に潰す

Private GitHubなのに、どうしてWebで見られるの？

Cloudflareのビルドシステムが、あなたが許可したGitHubリポジトリを読み、HTML/CSS/JSなどのデプロイ成果物をCloudflare側へ配置するからです。閲覧者がGitHub Private repoを直接読むわけではありません。

CloudflareはPrivate GitHubの中身をコピーするの？

概念的には「ビルド時にソースを取得し、配信用成果物をCloudflareへデプロイする」と理解すると正確です。GitHubは正本、Cloudflareは配信用コピー/成果物を保持します。

URLを知っている人全員が見られる？

Accessを正しく設定すればいいえ。Cloudflareはリクエストごとに有効なAccessトークンを確認し、なければログインへ誘導または拒否します。

独自ドメインは必須？

Workersでは必須ではありません。 workers.dev で開始でき、Accessで保護できます。ただしCloudflareは本番用途では独自ドメインまたはRouteを推奨しています。

LEVEL 3｜しっかり理解

ブラウザからHTMLが届くまで

「どこでAccessが止めているのか」を通信順に追います。

Private Knowledgeへアクセスする実際の流れ

  1. 1
    ブラウザがURLへアクセス

    例：private.example.com または保護された workers.dev URL。

  2. 2
    DNS が入口を案内

    独自ドメインならDNSによりCloudflareへルーティング。WorkersのCustom DomainではCloudflareがDNSレコードと証明書を設定できます。

  3. 3
    Cloudflareが先に受け取る

    ここがReverse Proxy / Edgeの位置。Originや静的アセットに届く前にCloudflareがHTTPリクエストを処理できます。

  4. 4
    Access が認証状態を確認

    保護されたサイトでは、各HTTPリクエストに有効な CF_Authorization Cookieがあるかを確認。なければHTMLを出さずログインへ。

  5. 5
    本人確認

    One-Time PIN やGoogle/Microsoft/Okta等のIdentity Providerで本人を確認します。

  6. 6
    Access Policyで許可判定

    メールアドレス・メールドメイン・グループ・端末条件などを評価。Access applicationはdeny by defaultで、Allowに一致した人だけ通ります。

  7. 7
    許可されたらHTMLを返す

    Workers Static Assetsのファイルを返す、またはWorker処理へ進む。閲覧者はGitHubへアクセスしていません。

DNSをもう一段正確に

やさしい意味：住所案内↓DNS↓Domain Name System

ブラウザが「このドメインはどこへ通信すればよい？」と問い合わせ、権威DNSが最終的な記録を返します。Cloudflareを権威DNSにすると、DNSレコードをCloudflare側で管理できます。

プロキシ対象のDNSレコードでは、OriginのIPではなくCloudflareのAnycast IPを返し、HTTP/HTTPS通信をCloudflare経由にできます。

Reverse Proxyをもう一段正確に

やさしい意味：前に立つ受付↓Reverse Proxy↓ClientとOriginの間で要求を代理処理

利用者はCloudflareに接続し、Cloudflareが必要に応じてOriginへ接続します。これによりOrigin IPの秘匿、TLS終端、キャッシュ、WAF、Access等を途中で適用できます。

Cookie

ブラウザがサイトごとに保持する小さなデータ。Accessでは CF_Authorization に署名済みJWTが入ります。

「ログイン済みとして扱う期間」。AccessにはGlobal tokenとApplication tokenがあり、期限切れで再認証が発生します。

SECURITY｜重要

「Accessを付ければ何でも置ける」ではない

ここはPrivate Knowledgeで最も重要な境界です。

危険

Accessは強力な入口だが、データ分類の代わりではない

Accessは「許可された人以外を入口で止める」仕組みです。しかし、設定ミス、アカウント乗っ取り、誤共有、端末紛失、ブラウザからの保存・スクリーンショット、Git履歴への残存など、別の漏えい経路は残ります。

低〜中機密

限定共有の知識HTML

家族内メモ、一般には出したくない学習情報、個人名を含むが致命的ではない内容。

候補：Private GitHub + Workers Static Assets + Access + OTP/IdP。

高機密

医療・詳細な個人情報

診療情報、心理検査、住所、詳細な家族情報など。法令・契約・組織ポリシーが絡む可能性があります。

追加検討：MFA、短いSession、最小権限、監査、端末管理、暗号化、保存場所、データ処理契約。

最高機密

秘密鍵・パスワード・認証情報

API Secret、秘密鍵、復旧コード、金融認証情報など。

原則：HTML/Gitへ置かない。専用Secret Manager / Password Manager等へ分離。

Private KnowledgeをGitHub Pagesへ置くのが危険な理由

GitHub公式は、GitHub PagesサイトはリポジトリがPrivateでも通常インターネット上で公開されると警告しています。GitHub Enterprise CloudにはPrivate Pages機能がありますが、一般の個人運用で「Private repoだからPagesもPrivate」と考えるのは危険です。

覚え方：「リポジトリの公開範囲」と「Webサイトの公開範囲」は別設定。

将来、Private Knowledgeを作る時の最低限チェック

  • GitHub repositoryはPrivate
  • Cloudflare GitHub Appは対象repoだけ許可
  • Worker/hostnameにAccessを設定
  • Allow policyは必要なメールだけ
  • OTPまたは信頼するIdPを設定
  • Session durationを必要以上に長くしない
  • workers.dev / Preview / Custom Domainの「抜け道」がないか確認
  • SecretはHTMLやGitに入れない
  • 公開URLをログアウト/シークレット環境で検証
  • 高機密データは別の保存方式も検討

最初の疑問に一問一答

Cloudflareってサーバーなの？

「1台のサーバー」ではなく、世界中のサーバーとネットワークを使うプラットフォーム。DNS、CDN、Reverse Proxy、Workers、Accessなど複数の役割があります。

GitHub Pagesと何が違う？

GitHub PagesはGitHubから静的サイトを公開する機能。Cloudflareは配信だけでなく、通信の入口、認証、防御、サーバーレス実行まで担当できます。

Netlifyとは何が違う？

NetlifyもGit連携・静的/フルスタック配信・限定公開機能を持つ競合サービスです。CloudflareはDNS・Reverse Proxy・Zero Trust Access・世界規模ネットワークとWorkersを一体化しやすい点が今回の設計に合います。

Accessはどこで止めている？

アプリのHTMLやOriginへ到達する前、Cloudflareのネットワーク上でHTTPリクエストを評価します。Worker保護では「Workerが走る前」にAccessがチェックします。

Gmail以外でもOTPは使える？

はい。Access Policyで許可された受信可能なメールアドレスなら、Gmailに限定されません。

家族数人だけなら無料？

Zero Trust Freeは50ユーザー上限なので、人数面では家族数人は範囲内です。Workersや他機能には別のFree上限があるため、実装時に再確認します。

*.workers.devでもAccessできる？

はい。2026年8月現在、workers.devのproduction/previewをAccessで保護できます。Worker単位保護なら関連するworkers.dev・Custom Domain・route・previewをまとめて保護できます。

*.pages.devは？

Pagesの既定URLとして利用できます。Pagesは継続利用可能ですが、新規静的サイトはWorkers Static Assetsが公式推奨です。Private Knowledgeの新規設計ではWorkers側を優先します。

CloudflareだけでHTMLを置ける？

はい。GitHubを使わずWrangler等で直接Workers Static Assetsへdeployできます。ただし履歴・差分管理を考えるとGitHubを正本にする利点があります。

医療情報なら何でもAccessへ置いてよい？

いいえ。Accessは認証レイヤーであり、法令・契約・保存地域・監査・端末管理・MFA・Git履歴などの要件を自動的に満たすわけではありません。高機密情報は別途リスク評価が必要です。
