LEVEL 2

3〜5分で「作り方」を理解する

1. まず、道具を役割で理解する

ChatGPT / Sol

やさしい意味：設計者・レビュアー

正式には生成AI。要件整理、データモデル、原因分析、UX判断、リスク評価、PRレビューなど「考える比重が高い仕事」を担当。

Codex

やさしい意味：PCで手を動かす開発担当

リポジトリを読み、複数ファイル編集、コマンド実行、テスト、Git操作、PR準備を行う。採択済み仕様を勝手に再設計しない。

GitHub

やさしい意味：コードの正本と作業記録

repository、commit、Issue、branch、Pull Requestで「いつ・なぜ・何を変えたか」を残す。

GitHub Pages

やさしい意味：静的Webの公開場所

HTML/CSS/JavaScriptを配信する。サーバー側処理や秘密情報の保管場所ではない。

Supabase

やさしい意味：共有データ倉庫＋ログイン

PostgreSQL、Auth、API等を提供。Second Brain Bridgeでは端末間同期とアカウント境界を担う。

PC Agent

やさしい意味：ブラウザの外で動く作業員

Node.js / PowerShell等で、ローカルファイルやブラウザ自動操作などWebページだけでは難しい処理を担当。

Obsidian

やさしい意味：長期保存の本棚

Bridgeの現在状態とは別にMarkdownを保存。Second Brain BridgeのAgent v1は一方向・追記型で既存ノートを壊さない。

2. 開発はこの一本道で進める

  1. 課題を1文にする

    「誰が、どんな場面で、何に困っているか」。機能名から始めない。

  2. MVPを決める

    MVP = Minimum Viable Product。最初に価値を確認できる最小構成。将来機能は別枠に逃がす。

  3. データの正本を決める

    ブラウザ、Supabase、GitHub、Obsidianのどれが何の正本かを先に固定する。

  4. GitHubリポジトリを作る

    本格Webアプリは原則1アプリ=1リポジトリ。READMEと開発ルールを先に置く。

  5. ChatGPTで仕様を固める

    未決定事項、例外、安全条件、受け入れ条件まで言語化する。

  6. Codexへ実装を渡す

    既存コードを読ませ、採択済み仕様だけを実装。変更ファイルとテスト結果を報告させる。

  7. 小さく動かす

    まずブラウザ内保存だけ、次にクラウド同期、次に外部連携、と境界ごとに増やす。

  8. テストを契約にする

    「動いた」だけでなく「壊してはいけない挙動」を自動テストにする。

  9. PRでレビューする

    重要変更はmainへ直書きせず、diffとCIを見てGO / 修正を判断する。

  10. 公開後に実環境smoke

    GitHub Pages、iPhone、Windows、実ログイン等、本番でしか分からない箇所を最小確認する。

  11. 運用を1クリック化する

    PowerShellやNodeコマンドを、最終利用者には .cmd 等の入口へ隠す。必要なら後で定期実行化する。

3. Second Brain Bridgeで実際に分離した「保存」

場所役割なぜ分ける？
ブラウザ保存すぐ使える端末側の現在状態オフラインや表示速度に強い
Supabaseログインした利用者のクラウド同期iPhoneとPCなど複数端末をつなぐ
GitHubアプリのコード・仕様・レビュー履歴データとコードの責務を混ぜない
ObsidianMarkdownの長期アーカイブBridgeで削除・リセットしても知識資産を安易に消さない
knowledge-html読むための完成知識HTML通常のBridgeデータに混ぜず、registryから読み取り専用で探す

専門用語1｜local-first / ローカルファースト

やさしい意味：まず手元の端末で使え、クラウドは同期役になる考え方。

正式な説明：ユーザー操作の主経路をローカル状態に置き、ネットワーク障害や遅延からUIを切り離しつつ、後でサーバー状態と整合させる設計。Second Brain Bridgeは端末状態とSupabase同期を両方扱うため、衝突・削除・アカウント切替をテスト対象にしている。

専門用語2｜tombstone / トゥームストーン

比喩：「削除した」という墓標だけ残す。

実際の仕組み：単純にローカルから消すと、別端末に残っていた古いデータが次回同期で復活することがある。そこで削除IDと削除時刻を記録し、同期相手にも削除を伝える。

正式名称：削除マーカー、tombstone record。Second Brain Bridgeではクラウド行の deleted_at とローカルtombstoneを突き合わせる。

専門用語3｜reset_epoch / リセット世代

やさしい意味：「全消去の前と後」を別の世界として区別する番号。

全リセット後に古い端末データが復活する事故を避けるため、クラウド側の世代番号を進める。Obsidian Agentでも account + reset_epoch + bridge_items.id を組み合わせ、同じIDがリセット後に再利用されても別アーカイブとして扱える。

B. 同期で一番怖いのは「消したものが戻る」こと

端末Aで削除
→
端末Bには古いデータが残る
→
次回同期
→
削除データが復活？
削除IDをtombstone化
→
クラウドにも削除時刻
→
各端末が削除を再現
→
復活を防ぐ

さらに全データリセットは通常削除とは別問題です。Second Brain Bridgeでは reset_epoch を使い、別世代のデータを混ぜないようにしています。

C. Obsidianを「同期先」ではなく「壊さないアーカイブ」にした理由

固定境界

一方向

Bridge / Supabase → Obsidian。AgentからBridgeへ処理結果を書き戻さない。

固定境界

append-only

既存Markdownを編集・移動・削除しない。同じidentityは2回作らない。

保持

削除と分離

Bridgeのtombstoneや全リセットを理由に、過去に保存済みのObsidianノートを消さない。

注意

現在状態とは違う

Obsidianは「今のBridgeの完全コピー」ではなく、Captureを残す長期アーカイブ。

identityの考え方

sha256(accountId + NUL + reset_epoch + NUL + bridge_items.id)

タイトルをファイル名にしないので、禁止文字・タイトル変更・別アカウント・リセット後ID再利用の衝突を避けられます。生のaccountIdはMarkdownへ書かず、ハッシュだけを監査用に残します。

D. PC Agentが必要になる境界

処理WebページだけPC Agent
画面表示・入力得意不要
Supabase API通信可能可能
WindowsのVaultへ直接Markdown保存制約が大きい得意

現状

「PCが常時ついている」だけでは自動実行にはなりません。現在の入口は X同期.cmd と Obsidian書き出し.cmd の1クリック実行です。定時実行や常駐化は、Windowsタスクスケジューラ等を別途設定して初めて自動になります。

E. X同期で学べる「外部サービス連携」の設計

  1. Supabaseの既存Bridge rowsを全件ページング取得。
  2. 全文取得済み・削除済み等を分類し、不要な外部アクセスを避ける。
  3. Xブックマーク一覧から新規だけ検出。
  4. 通常投稿とX Articleを必要な場合だけ全文化。
  5. 既存IDを照合し、安全にupdate / insert。
  6. 再取得して件数・本文長・全文フラグ・重複を検証。

重要なのは「取れたら保存」だけではありません。既存の人間編集を短い取得結果で上書きしない、成功済みArticleを毎回再fetchしない、失敗してもpreviewを残すといった反復運用の安全設計が必要です。

F. セキュリティで初心者が混同しやすい点

公開用キー ≠ パスワード

Supabaseのブラウザ向けpublishable keyはクライアントに置く前提のキーです。ただし「公開してよいキーだから無制限に安全」ではありません。AuthとRLSなどサーバー側制約が本体です。

秘密情報はGitHubへ入れない

.env.local、Cookie、トークン、パスワード、ブラウザセッション、個人ログはgitignore。Second Brain Bridge PC Agentもこの境界を採用しています。

画像URLはただの画像とは限らない

PC Agentの画像取得はprivate/reserved IP、redirect、サイズ、Content-Type、symlink等を検査。外部URLをサーバー/PCが取りに行く処理はSSRFなどの攻撃面になる。

G. テストは「機能確認」より「契約の固定」

構文チェックnode --check
targeted test今回触った機能を高速確認
full Node tests他機能への回帰を確認
CIGitHub Actions上の同一条件で再確認
real smokeiPhone / Windows / Xログイン等の実環境だけ最小確認

Second Brain Bridgeでは削除、reset、同期中編集、アカウント切替、Obsidian重複防止、media safety、X取得などを自動テスト化しています。これは機能数を増やすためではなく、将来のAIが既存契約を壊さないためです。

J. 初心者がやりがちな失敗

失敗1

最初から全部入り

認証、同期、AI、通知、自動化を一度に作ると、どの境界が壊れたか分からない。MVP→境界ごとの追加にする。

失敗2

「AIが直した」でmerge

変更理由・テスト・回帰・実環境条件を確認する。重要箇所は別AIレビューも使う。

失敗3

削除を単純DELETEで考える

複数端末同期では復活問題がある。tombstoneや世代管理を検討する。

失敗4

GitHubをデータベース代わりにする

コード・静的公開と、ユーザーが日常更新するデータは分ける。

失敗5

PowerShellを利用者に毎回打たせる

開発中のコマンドは必要でも、運用時は .cmd、ボタン、スケジューラ等に隠す。

失敗6

チャットだけを仕様書にする

採択済み仕様と受け入れ条件はREADME、docs、Issueへ残す。

理解チェック

3分で自己確認

Q1. ChatGPTとCodexは、同じ役割として使うのがよい？
答え：いいえ。 ChatGPT / Solは設計・判断・レビュー、Codexはリポジトリ上の実装・コマンド・テストを中心に分業すると効率がよい。
Q2. GitHub Pagesだけで、複数端末のユーザーデータ同期までできる？
答え：通常はできません。 GitHub Pagesは静的ファイル配信。日常的に変わる共有データにはSupabase等のバックエンドを組み合わせる。
Q3. 削除データを同期するとき、単純に端末から消せば十分？
答え：複数端末では危険。 古い端末から復活する可能性があるため、tombstone等で「削除した事実」を同期する設計が必要。
Q4. Bridgeで削除したら、Obsidianのアーカイブも自動削除する？
答え：現在のv1方針では削除しません。 Obsidian Agentは一方向・append-onlyで、Bridgeの現在状態と長期アーカイブを分離している。
Q5. PCを24時間つけていれば .cmd は自動で実行される？
答え：いいえ。 .cmdは実行入口です。定時自動化にはWindowsタスクスケジューラ等の別設定が必要。
次の一歩

別アプリを作るときは、まず機能一覧ではなく「設計シート」を1枚作る

問題 → MVP → データの正本 → 役割分担 → 壊してはいけない契約 → テスト → 公開後smoke。この順番を守るだけで、AI開発の迷子になりにくくなります。
